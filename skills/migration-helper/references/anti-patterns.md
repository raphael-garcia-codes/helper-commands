# Migration Helper Anti-Patterns

Read this before executing any migration stage. Remove anything that makes rollback vague, data unsafe, or breaking changes harder to review.

## 1. Mixed-Scope Migration

Bad signs:

- A framework upgrade includes unrelated UI cleanup.
- A schema migration ships with a new product feature.
- Test failures are hard to attribute because many changes landed together.

Why it hurts:

- Rollback may remove unrelated work.
- Reviewers cannot focus on migration risk.

Do instead:

- Keep migration stages separate from feature and cleanup changes.
- Land preparation, migration, and cleanup in reviewable units.

## 2. Destructive First Step

Bad signs:

- A production column is renamed or dropped in the same deploy that stops using it.
- Old API fields are removed before all consumers switch.
- A queue event shape changes without compatibility.

Why it hurts:

- Rolling deployments can run old and new code at the same time.
- Consumers can fail immediately when the old contract disappears.

Do instead:

- Use expand -> migrate/backfill -> contract.
- Remove old contracts only after new reads/writes are verified.

## 3. Autogenerated SQL Trust

Bad signs:

- ORM migration output is applied without reading the SQL.
- A generated rename is actually a drop-and-add.
- Index and constraint operations are accepted without checking locks.

Why it hurts:

- Autogenerate tools optimize for schema difference, not production safety.
- Data loss and table locks can hide behind friendly migration names.

Do instead:

- Read generated SQL.
- Rewrite unsafe operations into staged, non-blocking steps when needed.

## 4. Local-Speed Assumption

Bad signs:

- A migration is considered safe because it ran quickly on a small local database.
- Row counts, table size, lock behavior, and indexes are unknown.
- Backfill is one large transaction.

Why it hurts:

- Production data volume changes lock duration and resource use.
- Large writes can block users or exhaust resources.

Do instead:

- Check table size and lock risk before choosing the operation.
- Batch backfills and use non-blocking DDL where supported.

## 5. Skipping Major Versions

Bad signs:

- A library jumps from version 2 to 5 in one step without reading each guide.
- Codemods are skipped because manual editing feels faster.
- Peer dependency requirements are guessed.

Why it hurts:

- Breaking changes stack together and become hard to diagnose.
- Official upgrade tooling may only support adjacent versions.

Do instead:

- Follow official supported hops.
- Stabilize and verify after each major version.

## 6. Rollback Equals Revert

Bad signs:

- Rollback instructions say only "revert the PR".
- Data movement, external consumers, and deployed versions are ignored.
- Destructive steps have no recovery note.

Why it hurts:

- Code can be reverted faster than data can be restored.
- Reverting after partial rollout can make old and new data inconsistent.

Do instead:

- Define rollback per stage.
- State when rollback requires reverse migration, restore, or forward fix.

## 7. Unauthorized Database Action

Bad signs:

- A migration, query, or backfill runs without user permission.
- The database URL or environment is assumed.
- Production and local database commands are treated the same.

Why it hurts:

- The wrong database can be changed.
- Irreversible operations can run before the user approves risk.

Do instead:

- Ask explicit permission before any database operation.
- Confirm database URL and environment with the user before execution.

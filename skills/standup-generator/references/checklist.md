# Standup Generator Checklist

Use this checklist before writing an individual update, live talking points, or a team digest.

## Scope and Window

- [ ] Time window is explicit: today, yesterday, this week, sprint, or custom range.
- [ ] Output type is explicit: individual, team digest, async update, or live standup.
- [ ] Audience is known: manager, team, client, product, or cross-functional group.
- [ ] Team template or prior format is checked when available.
- [ ] Time zone is clarified when activity spans dates.
- [ ] The update does not include work outside the requested window unless marked as context.
- [ ] Sparse activity is handled honestly.

## Source Collection

- [ ] Git commits in the window are reviewed.
- [ ] PRs opened, merged, reviewed, commented, or blocked are reviewed.
- [ ] Ticket status changes are reviewed when a tracker is available.
- [ ] CI/build failures are included only when relevant to progress or blockers.
- [ ] User-reported context is labeled when not visible in tools.
- [ ] Meeting notes or chat context are used only when provided or accessible.
- [ ] Source gaps are called out instead of filled with guesses.
- [ ] Duplicate signals are merged: one PR may include several commits.

## Classification

- [ ] Blockers are identified first.
- [ ] Completed/shipped work is separated from in-progress work.
- [ ] Today/next work is separated from completed work.
- [ ] Risks and notes are included only when real.
- [ ] Reviews and support work are included when they consumed meaningful time.
- [ ] Waiting states name who or what can unblock them.
- [ ] Work is grouped by outcome, not by raw commit list.

## Specificity

- [ ] PR numbers are included when available.
- [ ] Ticket IDs are included when available.
- [ ] Counts are included only when supported by sources.
- [ ] Nouns are concrete: feature, endpoint, dashboard, migration, bug, review, test.
- [ ] Vague phrases like "worked on stuff" are removed.
- [ ] Technical detail is compressed for non-technical audiences.
- [ ] No intent or decision is inferred from branch names alone.
- [ ] No progress is invented to fill a section.

## Format Choice

- [ ] Live standup bullets are short and spoken-friendly.
- [ ] Async updates include enough detail to become a record.
- [ ] Client updates emphasize outcomes, blockers, and next steps.
- [ ] Team digests preserve attribution when useful.
- [ ] Board-style digests follow status columns when that is how the team works.
- [ ] Blockers appear first unless the team's established template says otherwise.
- [ ] Sections with no content are omitted or marked `None` only when useful.

## Tone and Accuracy

- [ ] The update is factual and calm.
- [ ] Blockers are direct, not hidden behind vague phrasing.
- [ ] Credit is attributed correctly in team digests.
- [ ] The update does not overclaim ownership of shared work.
- [ ] "Done" means merged, shipped, completed, or otherwise clearly finished.
- [ ] "In progress" means active but not done.
- [ ] "Next" means planned, not already completed.
- [ ] "Reported by user" context is not presented as tool-verified.

## Final Check

- [ ] A teammate can tell what changed.
- [ ] A teammate can tell what is blocked.
- [ ] A teammate can tell what happens next.
- [ ] The update is shorter than the raw activity list.
- [ ] Quiet windows are represented honestly.
- [ ] The output contains no unsourced decisions, blockers, or progress.
